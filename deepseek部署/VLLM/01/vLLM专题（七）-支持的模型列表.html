vLLM支持跨多种任务的生成式和池化模型。如果一个模型支持多个任务，您可以通过–task参数来设置任务。

对于每个任务，我们列出了已在vLLM中实现的模型架构。每个架构旁边，我们列出了一些使用该架构的流行模型。

1. 加载模型

1.1 HuggingFace 模型库

默认情况下，vLLM 会从 HuggingFace (HF) Hub 加载模型。

要确定某个模型是否受支持，您可以检查 HF 仓库中的 config.json 文件。如果 “architectures” 字段包含以下列出的模型架构，那么理论上该模型应该是受支持的。

提示
检查您的模型在运行时是否真正受支持的最简单方法是运行以下程序：

from vllm import LLM

# For generative models (task=generate) only
llm = LLM(model=..., task="generate")  # Name or path of your model
output = llm.generate("Hello, my name is")
print(output)

# For pooling models (task={embed,classify,reward,score}) only
llm = LLM(model=..., task="embed")  # Name or path of your model
output = llm.encode("Hello, my name is")
print(output)

如果 vLLM 成功返回文本（对于生成式模型）或隐藏状态（对于池化模型），则表明您的模型是受支持的。
否则，请参考 添加新模型部分，了解如何在 vLLM 中实现您的模型。或者，您可以在 GitHub 上提交问题，请求 vLLM 支持。

1.2 Transformers 后备方案

在合并 Pull Request #11330 之后，vLLM 可以回退到 transformers 中可用的模型。目前这并非对所有模型都有效，但大多数解码器语言模型已支持，视觉语言模型的支持也在计划中！

要检查后端是否为 transformers，您可以简单地执行以下操作：

from vllm import LLM
llm = LLM(model=..., task="generate")  # Name or path of your model
llm.apply_model(lambda model: print(model.__class__))

如果显示为 TransformersModel，则意味着它是基于 transformers 的！

1.3 支持的功能

1.3.1LORA 和量化

通常，transformers 模型通过 load_adapters API 加载权重，这依赖于 PEFT。我们需要做一些工作来使用此 API（目前这会导致某些权重未被标记为已加载）或相应地替换模块。

以下是实现方式的一些提示：

class TransformersModel(nn.Module, SupportsLoRA):
  def __init__(*):
    ...
    self.model.load_adapter(vllm_config.load_config.model_loader_extra_config["qlora_adapter_name_or_path"])

问题在于你需要指定支持的Lora层，而我们理想情况下希望能够加载检查点中的所有内容！

1.3.2 远程代码

这意味着，任何在模型库中能够在transformers中使用trust_remote_code=True并正确实现注意力机制的模型都可以在生产环境中使用！

from vllm import LLM
llm = LLM(model=..., task="generate", trust_remote_code=True)  # Name or path of your model
llm.apply_model(lambda model: print(model.__class__))

一个模型只需要以下两点：

from transformers import PreTrainedModel
from torch import nn

class MyAttention(nn.Module):

  def forward(self, hidden_states, **kwargs): # <- kwargs are required

    ...
    attention_interface = attention_interface = ALL_ATTENTION_FUNCTIONS[self.config._attn_implementation]
    attn_output, attn_weights = attention_interface(
      self,
      query_states,
      key_states,
      value_states,
      **kwargs,
    )
    ...

class MyModel(PreTrainedModel):
  _supports_attention_backend = True

后台发生的事情如下：

  1. 配置被加载。
  2. 从 auto_map 加载 MyModel 的 Python 类，并检查模型是否支持 _supports_attention_backend。
  3. 使用 TransformersModel 后端。参见 /model_executors/models/transformers，它利用了 self.config._attn_implementation = “vllm”，因此需要使用 ALL_ATTENTION_FUNCTION。

就这样！

1.4 ModelScope

要使用来自 ModelScope 的模型而不是 HuggingFace Hub，请设置一个环境变量：

export VLLM_USE_MODELSCOPE=True

并且使用 trust_remote_code=True。

from vllm import LLM

llm = LLM(model=..., revision=..., task=..., trust_remote_code=True)

# For generative models (task=generate) only
output = llm.generate("Hello, my name is")
print(output)

# For pooling models (task={embed,classify,reward,score}) only
output = llm.encode("Hello, my name is")
print(output)

2.2.1 文本嵌入（–task embed）

注意
ssmits/Qwen2-7B-Instruct-embed-base 的 Sentence Transformers 配置定义不正确。您应该通过传递 --override-pooler-config '{"pooling_type": "MEAN"}' 来手动设置均值池化。

注意
与基础版 Qwen2 不同，Alibaba-NLP/gte-Qwen2-7B-instruct 使用双向注意力。您可以通过设置 --hf-overrides '{"is_causal": false}' 来相应地更改注意力掩码。
另一方面，它的 1.5B 版本（Alibaba-NLP/gte-Qwen2-1.5B-instruct）尽管在模型卡上描述不同，但仍使用因果注意力。
无论是哪个版本，您都需要启用 --trust-remote-code，以加载正确的分词器。请参阅 HF Transformers 上的相关问题。

如果您的模型不在上述列表中，我们将尝试使用 as_embedding_model() 自动转换该模型。默认情况下，整个提示的嵌入将从对应于最后一个 token 的归一化隐藏状态中提取。

2.2.2 奖励模型（–task reward）


如果您的模型不在上述列表中，我们将尝试使用 as_reward_model() 自动转换该模型。默认情况下，我们直接返回每个 token 的隐藏状态。

重要提示
对于过程监督奖励模型，例如 peiyi9979/math-shepherd-mistral-7b-prm，池化配置应该明确设置，例如：--override-pooler-config '{"pooling_type": "STEP", "step_tag_id": 123, "returned_token_ids": [456, 789]}'。

2.2.3 分类（–task classify）


如果您的模型不在上述列表中，我们将尝试使用 as_classification_model() 自动转换该模型。默认情况下，类别概率是从对应于最后一个 token 的 softmax 隐藏状态中提取的。

2.3 多模态语言模型的列表

以下模态根据模型的不同而有所支持：

文本

图像

视频

音频

支持任意组合的模态，用 + 连接。

例如：T + I 表示模型支持仅文本、仅图像和文本与图像的输入。

另一方面，用 / 分隔的模态是互斥的。

例如：T / I 表示模型支持仅文本和仅图像输入，但不支持文本与图像的输入。

请查看此页面了解如何将多模态输入传递给模型。

重要提示
为了在每个文本提示中启用多个多模态项，您必须设置 limit_mm_per_prompt（离线推理）或 --limit-mm-per-prompt（在线服务）。例如，要启用每个文本提示最多传递 4 张图像：
离线推理：

llm = LLM(
    model="Qwen/Qwen2-VL-7B-Instruct",
    limit_mm_per_prompt={
            "image": 4},
)

在线服务：

vllm serve Qwen/Qwen2-VL-7B-Instruct --limit-mm-per-prompt image=4

注意
vLLM 目前仅支持将 LoRA 添加到多模态模型的语言主干中。

2.4 模型支持政策

在 vLLM，我们致力于促进第三方模型在我们生态系统中的集成和支持。我们的做法旨在平衡对稳健性的需求和支持广泛模型的实际限制。以下是我们如何管理第三方模型支持的方式：

社区驱动支持：我们鼓励社区贡献以添加新模型。当用户请求支持新模型时，我们欢迎社区提交拉取请求（PR）。这些贡献主要根据它们生成的输出的合理性来评估，而不是严格与现有实现（例如 transformers 中的实现）的一致性。征集贡献：来自模型供应商的 PR 我们将非常感激！

尽力保持一致性：虽然我们旨在保持 vLLM 中实现的模型与其他框架（如 transformers）之间的一定一致性，但完全对齐并不总是可行的。加速技术和使用低精度计算等因素可能会引入差异。我们的承诺是确保实现的模型是功能性的，并生成合理的结果。

提示
在比较 HuggingFace Transformers 中 model.generate 的输出与 vLLM 中 llm.generate 的输出时，请注意，前者会读取模型的生成配置文件（即 generation_config.json），并应用默认的生成参数，而后者仅使用传递给函数的参数。在比较输出时，请确保所有采样参数一致。
问题解决和模型更新：我们鼓励用户报告他们在使用第三方模型时遇到的任何错误或问题。建议的修复应通过拉取请求（PR）提交，并清楚地解释问题和提出解决方案的理由。如果一个模型的修复影响到另一个模型，我们依赖社区来突出并解决这些跨模型依赖关系。注意：对于修复错误的 PR，良好的礼仪是通知原作者，征求他们的反馈。

监控和更新：有兴趣的用户应监控特定模型的提交历史（例如，通过跟踪 main/vllm/model_executor/models 目录中的更改）。这种主动的方式有助于用户及时了解可能影响他们使用的模型的更新和变化。

选择性关注：我们的资源主要集中在具有显著用户兴趣和影响力的模型上。使用频率较低的模型可能会得到较少关注，我们依赖社区在其维护和改进中发挥更积极的作用。

通过这种方式，vLLM 促进了一个合作环境，核心开发团队和更广泛的社区共同贡献于我们生态系统中支持的第三方模型的稳健性和多样性。

请注意，作为一个推理引擎，vLLM 不会引入新模型。因此，vLLM 支持的所有模型在这方面都是第三方模型。

我们对模型有以下几种测试级别：

严格一致性：我们将模型的输出与 HuggingFace Transformers 库中模型在贪婪解码下的输出进行比较。这是最严格的测试。请参阅模型测试，查看通过此测试的模型。

输出合理性：我们检查模型的输出是否合理且连贯，通过测量输出的困惑度并检查是否存在明显的错误。 这是一个较为宽松的测试。

运行时功能性：我们检查模型是否可以加载并运行而不出错。这是最宽松的测试。请参阅功能性测试和示例，查看通过此测试的模型。

社区反馈：我们依赖社区提供关于模型的反馈。如果模型损坏或无法按预期工作，我们鼓励用户报告问题或打开拉取请求进行修复。其余的模型属于此类别。
